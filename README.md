# Updates Repository Service

Сервис репозитория обновлений конфигураций информационных баз **1С**.

Индексирует каталог с файлами обновлений, держит актуальный кэш в памяти и отдаёт клиентам информацию о доступных обновлениях: наличие пакета, конкретное обновление, потенциальные кандидаты, расположение файлов на диске.

---

## Текущее состояние

Сервис работает в режиме **двух параллельных реализаций API** — это осознанный этап внедрения в прод:

| Протокол | Назначение | Статус |
|----------|------------|--------|
| **gRPC** | Совместимость с уже существующими потребителями | Поддерживается |
| **REST** | Новый HTTP/JSON API для дальнейшей эволюции сервиса | Развивается (v1 готов, v2 в работе) |

Оба API живут в одном процессе и используют **общий слой бизнес-логики** (`BusinessLogic`). Так можно мигрировать клиентов на REST без простоя и без расхождения данных: индекс репозитория один, ответы строятся из одних и тех же сущностей.

```
┌─────────────────┐   ┌─────────────────┐
│   REST (HTTP/1) │   │   gRPC (HTTP/2) │
│  Controllers v1 │   │ GrpcService     │
│  Controllers v2 │   │                 │
└────────┬────────┘   └────────┬────────┘
         │                     │
         └──────────┬──────────┘
                    ▼
         ┌─────────────────────┐
         │   BusinessLogic     │
         │  UpdatesRepository  │
         │  + AutoRefresher    │
         └─────────────────────┘
                    ▼
         ┌─────────────────────┐
         │  Файловый каталог   │
         │  обновлений 1С      │
         └─────────────────────┘
```

## Возможности

- Сканирование файлового репозитория обновлений (`.cuc` и связанные файлы)
- Периодическое обновление индекса без перезапуска сервиса
- Поиск обычных и **переходных** (между редакциями) обновлений
- Подбор потенциально подходящих обновлений для текущей конфигурации ИБ
- Получение пути к файлам обновления по идентификатору
- Версионирование REST API (`/urs/v1/...`, `/urs/v2/...`)
- OpenAPI / Swagger UI в Development
- Запуск как Windows Service или обычное ASP.NET Core-приложение

## Структура решения

```
ServiceCloud.UpdatesRepositoryService.slnx
├── ServiceCloud.UpdatesRepository.BusinessLogic      # доменная модель и индекс репозитория
├── ServiceCloud.UpdatesRepository.BusinessLogic.Tests
├── ServiceCloud.UpdatesRepositoryService             # хост: REST + gRPC
└── ServiceCloud.UpdatesRepositoryService.Tests
```

| Проект | Роль |
|--------|------|
| `BusinessLogic` | `IUpdatesRepository`, парсинг каталога, индексы, модели `InfoBaseUpdate` / `InfobaseConfig` |
| `UpdatesRepositoryService` | HTTP-контроллеры, gRPC-сервис, middleware, hosted service автообновления |
| `*.Tests` | Модульные и интеграционные тесты |

## Конфигурация

Секция `Repository` в `appsettings.json`:

```json
{
  "Repository": {
    "Path": "\\\\server\\share\\update",
    "RefreshInterval": "00:30:00"
  }
}
```

| Параметр | Описание |
|----------|----------|
| `Path` | Корневой каталог файлового репозитория обновлений |
| `RefreshInterval` | Интервал пересканирования индекса |

Эндпоинты Kestrel (по умолчанию в Development):

| Имя | URL | Протокол |
|-----|-----|----------|
| Rest | `http://localhost:5072` | HTTP/1.1 |
| Grpc | `http://localhost:5073` | HTTP/2 |

## REST API (v1)

Базовый путь: `/urs/v1/updates`

| Метод | Путь | Описание |
|-------|------|----------|
| `GET` | `/count` | Количество обновлений в индексе |
| `GET` | `/` | Полный список обновлений |
| `GET` | `/contains` | Проверка наличия обновления для конфигурации |
| `GET` | `/concrete` | Конкретное обновление (`transitive` — переходное) |
| `GET` | `/potential` | Потенциально подходящие обновления |
| `GET` | `/location` | Путь к файлам обновления по `updateId` |

Swagger UI (Development): `http://localhost:5072/swagger`

---

## gRPC API

Контракт: `ServiceCloud.UpdatesRepositoryService/repository.proto`

Основные RPC:

- `GetUpdatesCount`
- `GetUpdatesList` (stream)
- `ContainsUpdate`
- `GetUpdate`
- `GetPotentialUpdatesList` (stream)
- `GetLocation`

Эндпоинт по умолчанию: `http://localhost:5073`

## Зачем два API сейчас

1. **Прод не ломаем** — текущие клиенты продолжают ходить по gRPC.
2. **Новый контур готовим параллельно** — REST (и следующие версии API) можно подключать постепенно.
3. **Один источник правды** — бизнес-логика общая, нет двух независимых индексов.
4. **Миграция под контролем** — после перевода потребителей REST можно сузить или выключить gRPC-слой без смены ядра сервиса.
